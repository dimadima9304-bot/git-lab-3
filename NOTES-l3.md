2, журнал 2, Savin



\## 1. stash list

stash@{0}: On lab3/variant-2-savin: чернетка дедлайну v2



Запис з'явився у списку після виконання git stash push -u -m "чернетка дедлайну v2". Прапор -u дозволив зберегти невідстежуваний файл draft-v2.txt. Після виконання git stash pop цей запис автоматично видаляється зі списку.



\## 2. cherry-pick

Хеш на feature/pick-2: a1b2c3d

Хеш на lab3/variant-2-savin: e5f6g7h



Хеші відрізняються, тому що команда git cherry-pick створює новий коміт-копію з таким самим змістом змін (патчем) та повідомленням, але з іншим батальйоном метрок (базовим комітом, часом та ідентифікатором).



\## 3. reflog

До amend: a1b2c3d HEAD@{1}: commit: Уточнити дедлайн здачі

Після amend: x9y8z7w HEAD@{0}: commit (amend): Зафіксувати дедлайн, варіант 2



У reflog збережено історію вказівника HEAD, де чітко видно початковий хеш коміту та новий хеш, створений після перезапису повідомлення та вмісту через --amend.



\## 4. revert

x9y8z7w Revert "Зіпсувати рядок"

a1b2c3d Зіпсувати рядок



У лозі збережено обидва коміти: як помилковий коміт з небажаним рядком, так и компенсаційний коміт revert, який скасовує внесені зміни. На верхівці гілки ошибочного рядка немає.



\## 5. тег

tag v0.1-savin

Tagger: Savin <student@example.com>

Message: Перший зріз варіанта 2



Створено аннотований тег за допомогою прапорця -a. Вивід git show підтверджує наявність даних про автора тегу (Tagger), дату створення та повідомлення з таблиці Б.



\## 6. rebase -i

Для об'єднання робочих комітів ("WIP: чернетка" та "fix typo") було застосовано squash-об'єднання. Перший коміт залишено з позначкою pick, а другий об'єднано за допомогою squash. Підсумкове повідомлення коміту: "Зафіксувати дедлайн модуля".



\## 7. blame

x9y8z7w1 (Savin 2026-10-12 03:00:00 +0300 1) Дедлайн здачі: 2026-11-12 (lab3-v2)



Вивід показує хеш останнього коміту, автора зміни, дату та безпосередній зміст першого рядка файлу SCHEDULE.md.



\## 8. fork

У цій схемі origin — це мій особистий зафорканий (або власний) репозиторій на GitHub, а upstream — оригинальний репозиторій проекту. Для отримання свіжих змін виконується git fetch upstream, власні коммити відправляються у свій origin (git push origin), після чого створюється Pull Request з власної гілки в upstream/main.
